# 性能实现与测量

0.8.0 对编辑计数/章节使用按修改范围更新的索引；编辑器本身虚拟化显示，目录分批呈现，编辑状态最多驻留八个。修改正文使用延迟文本序列化，保存时才物化完整文本。配置目录索引、解析结果和单文件生效配置缓存按内容或文件树修订失效。

大于 120K 字符的纯文本/代码阅读按最多 12K 字符的区块组织，避开 Unicode 代理对边界；分页保留当前区块，滚动保留邻近最多三个区块及高度占位。全文仍完整保存在文档中。阅读区块缓存最多四本、约 8M 字符；布局缓存按字号、留白、窗口、标题页规则分别维护，最多三个。

分页总页数分批后台计算，可随离开阅读取消。未计算的总页数或前缀页码显示 `…`，不提供伪造精确值。滚动页数按视口和逐步校正的高度估算，正文位置用文本锚点保存。翻页动画只复制当前短区块；PDF 仅渲染可见的一至两页、限制渲染像素密度，离开后取消任务。Markdown/HTML 的复杂布局仍由 Web 引擎完成，没有和纯文本相同的区块化能力。

可运行 `node tests/performance-browser.mjs` 测量 60K、600K、2M 字符的打开、20 次输入、保存、阅读打开和十次翻页，结果写入忽略的 `test-results`。这是一台 Windows 桌面 Chromium 的对比，不能代表手机/平板或所有设备。`performance.memory` 会受垃圾回收、撤销历史和缓存影响，单次数值不能证明内存节省。

原 0.7.1 桌面基线中 2M 字符分页阅读打开约 9.9 秒、翻页 P95 约 1.1 秒；0.8.0 联调测得约 0.24 秒和 9–12 毫秒。后续测量会因并行测试和机器负载波动。功能测试另外检查跨区块章节跳转、搜索、字体/窗口变化和位置恢复。

数据与恢复文件保留在应用内部；缓存可重建但不删除正文或用户配置来达成性能目标。单文档 8 MB 和批量工作区 64 MB 等原有限制继续存在。

## 0.9.0 正文候选索引

正文候选采用独立 Worker、约 4K 字符分块和局部增量重建；候选数与每块条目均有上限。2M 字符首次后台索引约 6.3 秒，20 次编辑的最慢帧约 27ms，增量只传约 4K 字符；停用释放 Worker。属于本机桌面样例，不代表手机性能或精确词性判断。执行 `node tests/noun-performance-browser.mjs` 可复核；完整参数、限制与证据见 [分镜核对记录](STORYBOARD-AUDIT.md)。

新版识别改为按证据类型全局筛选并加入音译名识别，200 万字基准从约 500/1000 提高到约 990/1000，误报大幅减少；首次后台索引约 2–2.4 秒（Node），桌面浏览器输入 P95 约 11 毫秒。方法、基准、真实稿件对照与限制见 [正文名词候选基准](NOUN-BENCHMARK.md)。
